# EduBuddy specification

EduBuddy turns a student's lecture notes into topics, quizzes, explanations of weak topics and a short study plan. Sign-in is required: every API call carries a verified Firebase ID token, the token's uid is the profile id, and teacher and admin rights come from custom claims on that token. This document is the contract every part of the code is built to. When code and this document disagree, fix one of them in the same change.

## 1. The flow

Six screens, in a straight line, with one loop back.

1. Dashboard, route `/`. Home page. Recent notes, overall mastery, a "Review today" queue, latest feedback. Two actions: "Upload notes" and "Try sample notes". A first-time visitor sees an empty state that points at upload. The "Review today" queue (Phase 3) lists at most five topics to work on now: weak topics first, lowest mastery first, then topics not practised for `REVIEW_STALE_DAYS` (3) days or more, oldest first, with a topic that has progress but no attempt counting as oldest. Each item links to its study page and says why it is listed ("Weak", or the days since it was last practised). The queue is built in the browser from the progress list by `buildReviewQueue(progress, now)` in `src/lib/review.ts`, and it replaces the separate weak-topic list, so no topic appears twice on the dashboard. When there is progress but nothing to review, the queue says so in one line; with no progress at all it is not shown.
2. Upload, route `/upload`. Drop a PDF or paste text. Title is filled from the file name and can be edited. Analysis runs and the app moves to the Topics screen by itself. Scanned PDFs (Phase 3): when in-browser extraction finds fewer than `MIN_EXTRACTED_CHARS` (200) characters, the form tells the student that no readable text was found and that the PDF itself will be sent for reading, and on submit posts it as base64 to `/api/analyze-pdf` instead of `/api/analyze`. That path only accepts files of at most `MAX_PDF_BYTES` (3 MiB); a larger text-free PDF gets a message asking for a smaller file or pasted text. PDFs with readable text keep the browser-side limit `MAX_UPLOAD_PDF_BYTES` (25 MiB).
3. Topics, route `/notes/[id]`. The extracted topics with a one-line summary each, all selected by default, one button "Start quiz". Past scores for these notes below. Mastery overview (Phase 3): each topic card also shows the topic's mastery from the progress list, as a bar with the percentage, a "Weak" badge when the topic is weak, or the words "Not practised yet" when there is no progress for it. The bars are the only additions; the checkboxes stay one per topic and nothing else on the screen changes.
4. Quiz, route `/notes/[id]/quiz?quiz=<quizId>`. One question at a time, four options, progress bar, submit at the end.
5. Results, route `/notes/[id]/results?attempt=<attemptId>`. Score, per-topic bars, weak topics flagged, then three actions: "Study weak topics", "Practise weak topics", "Dashboard".
6. Study, route `/study/[materialId]/[topicId]`. The plain-language explanation for one topic, its key points, one action "Practise this topic".

Every screen has exactly one primary action. Secondary actions are visually quieter. The app must be usable on a phone.

## 2. Identity: Firebase sign-in required

The short version: a verified Firebase ID token is the only identity, the token's uid is the profile id, and roles ride on the token as custom claims.

- Every API request except `/api/status` must carry the token in an `Authorization: Bearer` header. The server verifies it with the Firebase Admin SDK (`authenticateRequest` in `src/lib/auth.ts`) and scopes every read and write to the token's uid (see `src/lib/api.ts`). A request for another profile's material, quiz or attempt gets 404, never the data.
- A missing token answers 401 ("Sign in is required"); an invalid or expired token answers 401. With `FIREBASE_SERVICE_ACCOUNT_JSON` unset every token-checked request answers 503 ("Authentication is not configured"): there is no guest fallback and no anonymous mode.
- Roles are `student`, `teacher` and `admin`, read from the token's `role` custom claim (anything else means `student`). Claims are set only through the Firebase Admin SDK, by running `node scripts/promote-role.mjs <email> <teacher|admin>` manually with `FIREBASE_SERVICE_ACCOUNT_JSON` set; the promoted user must sign out and back in to pick the new role up. `withRole` (in `src/lib/api.ts`) guards the teacher and admin routes: no token still gets 401 from the underlying auth, a signed-in user with the wrong role gets 403.
- The verified display name comes from the token, never a browser header, and is written onto the profile whenever it changes (trimmed to 80 characters).
- Two clients exist. The teammates' Vite preview frontend (`frontend/`) signs in with Firebase Authentication and sends the Bearer header; it needs `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID` and `VITE_FIREBASE_APP_ID` in `frontend/.env.local`, and renders blank without them. The Next.js app's own screens are not token-aware yet: they still send the legacy `x-profile-id` header (`src/lib/profile-client.ts`, kept on disk but ignored by the server) and currently surface sign-in-required errors. That state is accepted for now; a rework is possible later. Progress therefore belongs to the signed-in account, not to a browser.

## 3. Data

Types live in `src/lib/types.ts`. Storage goes through the `Store` interface in `src/lib/store/types.ts`, implemented by `MemoryStore` (the fallback when either Firebase setting is missing) and `RtdbStore` (both the service account and `FIREBASE_DATABASE_URL` set). Route code never imports either implementation directly; it calls `getStore()`. Authentication sits in front of the store: `withProfile` verifies the token (section 2) before any store call, and the profile id handed to every store method is the token's uid. The interface includes `getAttempt(id)` (Phase 3), which returns one attempt or null; the route that uses it compares the attempt's `profileId` with the caller's and answers 404 on a mismatch. `updateProfile(id, patch)` and `listProfileIds()` exist for the display-name sync and the teacher and admin aggregations. In both implementations `getOrCreateProfile` writes `lastSeenAt` only when the stored value is older than ten minutes, so a busy session does not write on every request.

Realtime Database layout, with `{profileId}` being the signed-in user's Firebase uid: `profiles/{profileId}`, `materials/{profileId}/{materialId}`, `chunks/{materialId}/{chunkId}` (the chunk id is the chunk order), `quizzes/{materialId}/{quizId}`, `attempts/{profileId}/{attemptId}`, `topicProgress/{profileId}/{topicId}`. Dates are ISO strings. A plain `get()` has no server-side ordering or filtering, so the list and lookup methods fetch a collection's children once and sort or filter in code (materials and attempts newest first, chunks by their order field); fields stored as null (absent children in the Realtime Database) are normalized back to null on every read.

Mastery rule: for a topic, `mastery = correct / (correct + wrong)` over all attempts. A topic is `weak` when mastery is below 0.6 and at least 3 questions have been answered. Both values are stored on `TopicProgress` and recomputed on every graded attempt.

Text handling: uploaded text is capped at `MAX_TEXT_CHARS` (300000, defined in `src/lib/constants.ts`). It is split into chunks of about 6000 characters on paragraph boundaries (see `splitIntoChunks` in `src/lib/ai/text.ts`) and stored in order. Quiz and explain calls send only the chunks relevant to the chosen topics; when relevance is unknown, send the first chunks up to a budget of about 24000 characters.

## 4. API routes

Request and response shapes are in `src/lib/api-types.ts` and are the contract. All routes are under `src/app/api`. All use `withProfile` from `src/lib/api.ts` except `/api/status`, which stays public. `withProfile` applies the IP limit, then verifies the Firebase ID token and loads or creates the profile for the token's uid before the handler runs (section 2); no route reads the old `x-profile-id` header. Input is validated with zod through `parseBody`. AI calls go through `consumeAiCall` first, so the daily cap applies.

| Route | Method | Purpose | Owner |
| --- | --- | --- | --- |
| /api/status | GET | Which backends are live (public, no token) | done |
| /api/analyze | POST | Create a material and extract topics | ingest |
| /api/analyze-pdf | POST | Scanned-PDF fallback: transcribe a base64 PDF and extract topics | ingest |
| /api/materials/[id] | GET | Material with attempts and progress | ingest |
| /api/quiz | POST | Generate and store a quiz, return it without answers | quiz |
| /api/quizzes/[id] | GET | Fetch a quiz again, without answers | quiz |
| /api/attempt | POST | Grade answers, store the attempt, update progress | quiz |
| /api/attempts/[id] | GET | Fetch a graded attempt again | quiz |
| /api/explain | POST | Explanation of one topic, cached on progress | insight |
| /api/feedback | POST | Study plan from progress, saved on the profile | insight |
| /api/me | GET | Dashboard data: profile, materials, progress, latest feedback, stats, and the profile's attempts (AttemptSummary, newest first, last 20) for the Progress page | insight |
| /api/notes | POST | Study notes for one material: sections, summary, key points, flashcards, cached on the material | UI port: backend |
| /api/chat | POST | One AI tutor reply with suggestions; history stored per profile | UI port: backend |
| /api/chat | GET | The profile's stored chat history | UI port: backend |
| /api/teacher/classroom | GET | Class roster for the Teacher Dashboard: per-student mastery, status, weak topics, weakness rows (teacher role) | UI port: backend |
| /api/admin/overview | GET | School-wide analytics and alerts for the Admin Dashboard (admin role) | UI port: backend |

The two role-guarded routes wrap their handlers in `withRole("teacher")` and `withRole("admin")`, which run the same `withProfile` pipeline first: a signed-in caller with the wrong role gets 403, a caller without a token gets 401.

`/api/notes` takes `{ materialId, refresh? }` and answers `{ notes, flashcards, cached }` where `notes` is `{ title, sections: [{heading, content}], summary, keyPoints }` and each flashcard is `{front, back}`. It counts one AI call, 404s on an unknown or foreign material, caches its output on the material document the way `/api/explain` caches on progress, and `refresh: true` bypasses the cache. The Notes screen renders the three tabs from this one response.

`/api/chat` POST takes `{ message, materialId?, history }` where `history` is the caller's last 10 messages (`{role, content}`), and answers `{ reply, suggestions }` with 0 to 3 short follow-up suggestions. It counts one AI call. The server appends the user message and the reply to the profile's stored history (last 50 messages kept). GET returns `{ messages }`. DELETE clears the profile's stored history and answers `{ messages: [] }`. Storage is the Firebase Realtime Database when both the service account and `FIREBASE_DATABASE_URL` are set, the in-memory store otherwise; the browser never talks to Firebase for data, only for sign-in (section 2).

The quiz responses (`/api/quiz` and `/api/quizzes/[id]`) carry the answer key per question (`correctAnswerIndex` and `explanation` in each public question) from the UI port on: the Quiz screen's "Check Answer" step reveals them client-side. Grading stays server-side and authoritative in `/api/attempt`. Accounts exist now, but the app is still a practice tool with no stakes, so the exposed key is accepted. `difficulty` (already in `QuizRequest`) is honoured: the AI prompt pitches the questions at the requested level; the mock treats it as cosmetic.

Grading rules for `/api/attempt`: every question in the quiz must be answered exactly once; `chosenIndex` must be 0 to 3; `score` is correct divided by total; after grading, `TopicProgress` is updated for every topic in the quiz and the response carries the per-topic result computed from the updated progress. In each `TopicResult`, `correct` and `total` count this attempt's questions on that topic, while `mastery` and `weak` are the cumulative values after the update. Each `QuestionResult` also carries the question's `stem` and `options`, so the Results screen needs only the attempt and never has to fetch the quiz again (this addition to `api-types.ts` is made by the quiz owner in Phase 2 together with the fixtures and the Results screen).

The "not ready" convention: a route that exists but is unfinished answers 501 with `{"error":"Not implemented yet"}`, and the screens show a calm placeholder for exactly that message. A route that does not exist yet answers 404, which the screens show as an error, so every planned route must exist at least as a 501 stub.

Sample notes: `/api/analyze` accepts the sample text like any other text. The Upload and Dashboard screens send the bundled sample (`src/content/sample-notes.ts`) with `sourceName: "sample"`. In mock mode the mock AI recognises the sample and returns its pre-computed topics. With real OpenRouter (Gemma) the sample is analysed live like any other notes.

Scanned PDFs (Phase 3): `/api/analyze-pdf` takes `AnalyzePdfRequest` (`title`, `pdfBase64`, optional `sourceName` and `pageCount`) and answers with the same `AnalyzeResponse` as `/api/analyze`, status 201, so the Upload screen handles both routes the same way. Validation: the title rules of `/api/analyze`; `sourceName` at most `MAX_SOURCE_NAME_CHARS` characters, default "upload.pdf"; `pdfBase64` is standard base64 of at most `MAX_PDF_BASE64_CHARS` characters (4 MiB, exactly the base64 length of a 3 MiB file) whose decoded bytes are at most `MAX_PDF_BYTES` and start with `%PDF`; anything else is 400 with a plain message. The route counts one AI call, asks `extractTopicsFromPdf` for the transcribed text and the topics, stores the text as chunks exactly as pasted text is stored (`charCount` is the transcription length, `pageCount` comes from the request, `status` is `ready`), and returns the material. The base64 cap keeps the JSON body small enough for serverless request limits. The scanned-PDF job is retired in the OpenRouter AI client (Gemma cannot receive PDF bytes), so with a real key the route answers 503 carrying the client's student-readable message; in mock mode it works as described here.

## 5. AI layer

Everything AI lives under `src/lib/ai`. Route code calls `getAi()` and never touches the SDK. The `AiClient` interface has four jobs:

- `extractTopics({ title, text })` returns 4 to 8 topics. Each has a short name (at most 6 words), a one-sentence summary, and 3 to 5 key points. Topic ids are URL-safe slugs of the name, unique within the material.
- `generateQuiz({ topics, chunks, count, difficulty, focusTopicIds })` returns `count` multiple-choice questions, each tied to one of the given topics, with exactly four options, one correct `answerIndex`, and a one or two sentence explanation. Questions must be answerable from the notes. When `focusTopicIds` is set, at least 70 percent of questions target those topics.
- `explainTopic({ topic, chunks, wrongQuestions })` returns a plain-language explanation of 150 to 300 words for a student who got it wrong, plus 3 to 5 key points. It should address the misconceptions visible in `wrongQuestions` when any are given.
- `generateFeedback({ progress, materials })` returns a study plan of 80 to 150 words: what is strong, what is weak, and the next two things to do.
- `extractTopicsFromPdf({ title, pdfBase64, sourceName })` (Phase 3) returns `{ text, topics }`: the notes transcribed as plain text in reading order, at most 30000 characters (a longer document is transcribed from its start up to that limit), and the same 4 to 8 topics `extractTopics` would return for that text. The mock returns a fixed note saying the PDF had no readable text and topics built from the file name, so the flow works without a key. The OpenRouter client has retired this job: Gemma is reached through chat completions, which accept text messages only, so the PDF bytes cannot be handed over; the client throws `AiError` with a student-readable message telling the student to upload a PDF with selectable text or paste the notes, and `/api/analyze-pdf` surfaces it as a 503.
- `generateNotes({ title, topics, chunks })` (UI port) returns `{ title, sections, summary, keyPoints, flashcards }`: study notes written from the material: 4 to 8 sections each with a heading and an 80 to 200 word body in plain language, a 40 to 80 word summary, 5 to 8 key points, and 6 to 10 flashcards each with a question front and a short answer back. Answer only from the notes.
- `chatTutor({ message, contextText, history })` (UI port) returns `{ reply, suggestions }`: a 40 to 150 word plain-language answer. When `contextText` (the active material's text) is present it answers from the notes; otherwise it answers as general study help. Suggestions are 0 to 3 short follow-up questions. The mock builds deterministic replies from the material's topics when a material is active and from a fixed general-help template otherwise.

OpenRouter implementation (`src/lib/ai/openrouter`): plain `fetch` calls to `https://openrouter.ai/api/v1/chat/completions`, authenticated with an `Authorization: Bearer OPENROUTER_API_KEY` header; no SDK. The model comes from `OPENROUTER_MODEL`; when it is empty the client tries `google/gemma-4-31b-it:free` first and, when that answers HTTP 429 or a quota/credits error, automatically retries the call once with the paid `google/gemma-4-31b-it`. `describe()` reports the model that actually answered (the free or the paid entry of the chain). Every job first asks for structured JSON output with a `response_format` of type `json_schema`, built from the JSON Schema conversion (`z.toJSONSchema`, root `$schema` key stripped) of the zod schemas in `src/lib/ai/schemas.ts`; if the API rejects `response_format` for the model, the client falls back to plain prompting and remembers that per model. Both paths parse and validate every response with zod; on failure the call is retried once with a corrective instruction, then fails with a clear error. HTTP failures map to student-readable messages: 401/403 a rejected key, 429 a busy service, 402 an out-of-credits account, 5xx a temporary outage.

Mock implementation (`src/lib/ai/mock`): deterministic, no network. It recognises the sample notes and returns their pre-computed topics; for other text it builds plausible topics from headings and paragraphs. Quizzes, explanations and feedback are built from the topics and key points with templates. Output must satisfy the same zod schemas.

Prompts live in `src/lib/ai/openrouter/prompts.ts`, written in plain English, and always state: answer only from the notes, keep language simple, output JSON that matches the schema, and no markdown.

## 6. Limits and protection

- `checkIpLimit`: 60 requests per minute per IP by default, overridable through the optional `IP_REQUESTS_PER_MINUTE` env variable (bounds 1 to 100000, invalid values fall back to 60). The robot e2e suite (parked, see section 7) used to raise it to 1000 for the server it started, because a full run makes roughly 65 profiled requests inside one minute from one IP. Rejected requests are logged to the server console as a warning before the 429 goes back.
- `consumeAiCall`: `DAILY_AI_CALL_CAP` (default 60) AI calls per profile, that is per signed-in user, per UTC day.
- Plain-number ceilings live in `src/lib/constants.ts`, which imports nothing and is safe to import from browser code; `limits.ts` re-exports the ones server code uses. `MAX_TEXT_CHARS` 300000, `MAX_TITLE_CHARS` 120, `MAX_SOURCE_NAME_CHARS` 200, `MAX_QUIZ_QUESTIONS` 20, `MIN_EXTRACTED_CHARS` 200, `MAX_PDF_BYTES` 3 MiB, `MAX_PDF_BASE64_CHARS` 4 MiB, `MAX_UPLOAD_PDF_BYTES` 25 MiB, `REVIEW_STALE_DAYS` 3. Quiz `count` defaults to 10.
- Nothing secret is ever sent to the browser. `/api/status` returns only booleans and the model name.

## 7. Configuration and modes

The short version: mock AI still needs no key, but Firebase sign-in is now a hard requirement for API access.

- `OPENROUTER_API_KEY`: empty means mock AI.
- `FIREBASE_SERVICE_ACCOUNT_JSON`: required for any API access. Missing, every route guarded by `withProfile` answers 503 per request and there is no guest fallback; the AI and store fallbacks do not change that.
- `FIREBASE_DATABASE_URL`: set together with the service account it switches the whole store to the Firebase Realtime Database (sections 3 and 4); without it the app stays on the in-memory store even though the API is otherwise fully usable.
- Frontend preview (`frontend/`): `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_APP_ID` in `frontend/.env.local` so the sign-in-capable client can talk to Firebase Authentication.

Optional tuning variables: `DAILY_AI_CALL_CAP`, `IP_REQUESTS_PER_MINUTE` (section 6) and `OPENROUTER_MODEL` (empty means the free Gemma first with the paid Gemma as the automatic quota fallback). Roles are not configured through env variables: `scripts/promote-role.mjs` assigns them (section 2).

The `RuntimeBadge` in the header shows "Mock AI" and/or "Memory store" whenever a fallback is active, so nobody mistakes mock output for the real thing. `npm run check` verifies both server secrets against the real services and prints the model in use (unset checks are reported as SKIPPED, not FAIL). `npm run list-models` prints the Gemma models OpenRouter lists publicly and the model chain the app would use. `npm run smoke:ai` runs the AI jobs (the six text jobs on the sample notes, and the scanned-PDF job on `robot/data/test.pdf`, which in real mode asserts the scanned-PDF retirement message instead of output) and validates the output shapes, in whichever mode the environment gives; it talks to the AI layer directly, so the auth change does not affect it.

Testing: the guest-flow route test scripts (`npm run test:routes`) and the Robot e2e suites (`npm run test:e2e`) are parked pending an authenticated rewrite; both still drive the API without a token and would fail against it. `npm run test:srs` still runs and passes (it covers the scheduler and browser-side deck logic, no API).

The check script must not delete anything, not even its own test data: the Realtime Database check writes and reads back one fixed node, `_health/check`, which is simply overwritten on every run.

The UI is a faithful port of the teammate's ui/ux design (reference checkout at `scratch/uiux-ref`, outside the repository): `src/app/ui.css` carries the design system nearly verbatim (its `:root` tokens, class names, animations and media queries; only the Google Fonts import became an Inter variable from next/font, plus the new `.navbar-menu-btn` for the mobile sidebar toggle). Screens are built from those classes with the reference's inline styling; framer-motion drives the animations, react-icons the icons, recharts the Progress chart. The shell is the fixed Sidebar plus Navbar (`src/components/shell`), with the RuntimeBadge badges in the navbar and the sidebar collapsing below 768px behind the hamburger. The old token-and-primitive system was retired with the old screens; `Badge` survives only inside RuntimeBadge.
